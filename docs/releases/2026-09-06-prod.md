# Release to prod, 2026-09-06

Promotes `dev` onto `prod` (`f8ce3280`, released 2026-08-21). The exact promoted SHA is recorded on the promote PR.

## Delivery mechanics

Merging the promote PR pushes `prod`, which triggers `.github/workflows/deploy.yml`: build `:prod` images, push to GHCR, SSH to the box, `deploy.sh prod` (`compose pull`, `up -d`, health-check, roll the image back if unhealthy). The api container runs `prisma migrate deploy` against the live prod database on boot via `apps/api/docker-entrypoint.sh`, so the three migrations below apply automatically on the first boot of the new image.

The release is additive end to end. There is no `NOT NULL` added to an existing column, no type change, no rename, no drop of anything, and no unique index over data that existed before today. That is the whole reason this set is unusually calm compared with the fourteen migrations of 2026-08-21.

Migration 2 is the only one that writes data, so it is the one worth reading closely. It does three things, and each is idempotent by construction rather than by luck:

1. It records one reading-history cutover instant per user and derives the first calendar day, in that user's own timezone, that is fully covered by the new write path. The insert ends in `ON CONFLICT (user_id) DO NOTHING`, and no existing row is ever refreshed.
2. It folds every book whose progress snapshot still holds a finish date into at most one legacy finished cycle. Each row carries `legacy_source_key` of the form `book-reading-progress-snapshot:<book_id>`, which is a unique index, and the insert ends in `ON CONFLICT (legacy_source_key) DO NOTHING`. A second run collides and skips.
3. It points every already-counted reading goal book at the finished cycle that qualified it. The update is guarded by `qualified_reading_cycle_id IS NULL`, so it only ever fills a hole and never moves a value it already set.

The backfill is deliberately conservative about what it claims to know. A legacy cycle carries only facts that already exist, the known start date and the known rating, and it stamps the book metadata with `provenance: legacy_current_metadata` because nobody can know what the title, page count or series looked like on the day the book was actually finished. Rereads that were erased by the old mutable model are not invented.

### Raw-SQL index strip-trap

Clean. There is no `DROP INDEX` anywhere in the release, so nothing needed stripping by hand. Migration 3 adds one hand-written partial unique index, `book_reading_cycles_active_book_idx`, taking the set from twelve to thirteen. `apps/api/src/core/database/raw-sql-indexes.test.ts` asserts all thirteen with their predicates, and all thirteen were confirmed present on the migrated prod copy.

CLAUDE.md section 6 was updated in the same range and already names all thirteen, so the doc and the test agree for once. The test file stays the list to trust when they drift.

## Pre-flight (prod copy)

`pnpm db:copy:prod` dumps the live prod database read-only and loads it into a throwaway local container on port 5434, then `migrate deploy` runs against real data.

- The live prod database was at 96 applied migrations, exactly the 96 in `prod`'s own tree, so there was no drift to reconcile before starting
- All three migrations applied, `migrate deploy` exit 0
- `migrate status` afterwards reports "Database schema is up to date!" at 99 migrations
- Thirteen of thirteen hand-written indexes present afterwards with their predicates intact
- The backfill was re-run against the already-migrated copy and changed nothing, which is the property the three `ON CONFLICT` and `IS NULL` guards are there to provide
- The new partial unique index was proven to hold its invariant: a second active cycle for a book that already has one is rejected
- Copy container and dump removed afterwards, since they hold real user data

The tables migration 2 can write to are `user_reading_history_state` and `book_reading_cycles`, both created minutes earlier by migration 1 and therefore empty when it starts, plus the new `qualified_reading_cycle_id` column on `reading_goal_books`. No table that existed before this release changes its row count, because no statement in the release inserts into one, deletes from one, or drops one.

## Headline features

- **A reading statistics page.** New route at `/[locale]/(app)/statistics`, backed by one endpoint, `GET /api/statistics/overview`. The response carries eighteen sections in a single round trip: headline numbers, the reading calendar, dynamics over time, records, insights, goal progress, library balance, series, and the taste breakdowns by author, genre, language, publisher and rating. A period can be a custom range, a year, the last twelve months or all time, and everything except all time can be compared against the period before it.
- **A reading calendar.** A heatmap and a month grid say when reading actually happened, a diary lists it, and clicking a day opens what was read on it through a second endpoint, `GET /api/statistics/reading-days/:date`.
- **Reading history rebuilt as immutable cycles.** A finished book used to be a mutable snapshot, so rereading one overwrote the record of the first read and the history of it was simply gone. Reading history is now an append-only sequence of cycles, each with its own state, dates, rating and a frozen copy of the book metadata as of completion. The two new tables carry that, the existing finished books were backfilled into legacy cycles, and a partial unique index enforces that a book is part-way through at most one read-through at a time. Per-book serialisation in the reading lifecycle coordinator handles ordinary concurrency; the index is what catches a write path someone forgot to route through it.
- **Lending several books to one person at once.** The contact drawer could only start one loan per pass, so five books meant five trips through the same form. The first step now picks several books at once, asking the server only for books the direction allows, and the second step applies one set of terms to all of them. The write goes to a new `POST /api/books/loans/batch`, which is all or nothing rather than best effort, because a half-applied batch would leave books marked as lent with no loan behind them. Every check runs before the first write, since Postgres aborts a transaction on the first failed statement and per-book failure would surface one conflict and then refuse every later query.
- **Loan filters that match the rest of the app.** The loans list takes a loan date range, an expected return date range and a note flag, in an advanced filters sheet with removable chips, and the two reminder switches that were pretending to be filters became their own `reminder=on|off` param. The loan history page got the same shape: search, a Filters button with a count, a sort select, outcome as quick chips, and direction, person and date ranges in a sheet with its own draft, so nothing refetches until Apply.
- **Contacts that behave like people.** Creating a contact from inside a loan dialog no longer stacks a modal on a modal; the picker reports the typed name upward and the dialog switches to a create step. A contact card counts the books that person is holding right now rather than every loan they ever had. The contacts list opens on the people you actually lend to, with archived ones behind the filters sheet. The "returned on time" figure now divides by the loans that had a deadline at all, so a loan that never carried a due date stops counting against the reader.
- **Spending statistics you can follow to the end.** The page has a display currency, resolved by shared code so the backend and the page always agree and a currency the data no longer carries degrades to one it does. Every block that shows a number carries the exact query that produced it, including the derived order state, so opening a figure lands on the same subset the figure was built from. Orders are linked by id rather than by an order number a user may never have filled in. Each section loads, refreshes and fails on its own, so a slow budget query no longer blanks the charts and a failed refetch keeps the last good numbers with a note above them. The three empty cases, nothing ever ordered, nothing in this period, and nothing in this currency, are told apart and worded differently.
- **A budget that can stop.** `POST /api/delivery/budgets/:currency/stop` closes the version covering a chosen month and deletes one that starts exactly on it. Earlier months keep the amounts they were judged against, which is what the versioned table is for, and versions scheduled after the stop month survive. Zero is not overloaded to mean "none": the minimum amount is still 0.01, and no budget is the absence of a covering version.
- **The publisher picker stays open when you click its field.** The input sits inside `PopoverAnchor`, so Radix counted a pointerdown on it as an interaction outside the popover and dismissed the list while focus reopened it, which read as a flash on every click. It is now guarded the way the author, store and contact pickers already were.

### Rollback

`deploy.sh` rolls the image back automatically if the container never turns healthy. It does not roll migrations back. For this release that distinction costs nothing, which is not usually true.

Every migration here is additive, so the previous image runs unchanged against the migrated schema. Prisma never issues `SELECT *`, it expands an explicit column list from the fields the generated client knows about, so the old image never asks for `reading_cycle_id` or `qualified_reading_cycle_id` and never looks at `book_reading_cycles` or `user_reading_history_state`. Nothing it does write can violate the new partial unique index, because that index covers a table the old image has no code for.

Compare with 2026-08-21, where the window for a useful rollback closed at the migration that dropped `book_deliveries` and the honest answer after that point was to roll forward. There is no such point in this release. If the new image fails to boot, the old one serves correctly on the new schema, and the only visible loss is the reading statistics page and the cycle history behind it.

The one thing a rollback does not undo is the backfill, and it does not need to. The legacy cycles and the per-user cutover rows sit in tables the old code cannot see, and rerunning the backfill on the next attempt is a no-op by the three guards described above.
